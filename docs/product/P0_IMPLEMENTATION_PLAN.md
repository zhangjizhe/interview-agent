# P0 实施计划

最后更新：2026-08-13
状态：等待产品负责人评审。本文件不等同于实现批准。

## 交付顺序

### P0-1：评估证据与技能状态基础

目标：在展示技能图表前，让每项评价都可解释、可归属、可持久化。

- 新增版本化技能分类和用户归属的目标岗位记录。
- 建立规范化的 `InterviewQuestion` 与不可变 `InterviewAnswer` 实体。`InterviewQuestion` 必须关联
  `InterviewTask` 或保留其来源快照；`InterviewAnswer` 必须以外键关联问题、候选人消息和面试。
- 新增不可变 `AssessmentEvidence`：以外键关联 `InterviewQuestion`、`InterviewAnswer`、面试和
  `EvaluationRun`；保存回答 Span/摘要、期待/观察证据、技能归属、评估定义版本、状态与幂等键。
- 新增规范化的候选人技能评估/状态表，并关联来源面试。
- 定义唯一权威评估生产者；收敛当前“单题评价 Controller”和“结束面试报告生成”均可写
  `Report` 的行为，禁止不同口径覆盖同一权威评价。
- 迁移期间保留现有面试、报告、资源归属和成本流程。

验收标准：

- 已完成面试能够生成并校验与真实回答关联的评估证据。
- 证据可沿 `Interview -> InterviewQuestion -> InterviewAnswer -> AssessmentEvidence` 回溯；
  追问通过父问题外键归因，不能仅依赖问题/回答文本匹配。
- 已发布的回答和评估版本不可原地覆盖；纠正、重评或模型升级必须追加新版本，并保留 supersedes 关系。
- 同一评估输入、不可变评估定义版本和运行模式的重复投递由幂等键去重，失败重试不会重复累计技能状态。
- 用户只能读取自己的目标岗位、证据和技能状态。
- 现有报告流程保持兼容，或有测试保护的迁移方案。
- Prisma migration、鉴权测试和评估合同测试通过。

风险：

- 现有生成题目和报告未必稳定提供技能标签。
- 旧自由文本报告的回填必须可选，并明确标记为低置信度。

### P0-1 评估生产与重跑策略

1. `AssessmentEvidence` 是技能状态的唯一输入；`EvaluationRun` 持有不可变的完整评价结果、报告内容和证据。
   现有唯一 `Report` 保留为单一候选人展示快照，只保存 `currentEvaluationRunId` 与展示投影，不作为历史记录。
2. 新建不可变 `EvaluationDefinition`，其版本或内容哈希必须覆盖 `evaluatorVersion`、`promptVersion`、
   `rubricVersion`、`modelProvider`、`modelVersion`、模型参数、运行模式（`FINAL`/`PRACTICE`/`PREVIEW`）
   以及必要的降级策略版本。不得仅以 `evaluatorVersion` 代表这些行为。
3. 新建 `EvaluationRun`，以
   `interviewId + inputRevision + evaluationDefinitionVersion + evaluationMode`
   建立唯一幂等范围，并记录 `PENDING`、`RUNNING`、`SUCCEEDED`、`FAILED`、`DEGRADED`、`SUPERSEDED` 状态。
   运行时发生 Provider/Model 降级时，必须生成对应有效模型配置的新的评估定义或运行版本，不能命中原模型运行。
4. 结束面试流程成为权威的“最终面试评价”生产者。单题评价 API 只能生成明确标记为 `PRACTICE` 或
   `PREVIEW` 的评估证据，不能直接覆盖最终 `Report` 或更新正式技能状态。
5. 权威运行失败时必须保存失败原因和输入修订，不得以 `0` 分或自由文本占位报告污染技能状态。
   允许重试相同运行或显式创建新版本运行；降级模型运行必须标记 `DEGRADED` 并降低置信度。
6. `Report.interviewId` 的唯一性继续表示“当前展示快照”，而非历史唯一版本。新的成功 `FINAL`
   运行只在显式切换 `currentEvaluationRunId` 后更新展示投影；历史完整结果始终保留在 `EvaluationRun`。
   禁止使用 `upsert` 用不同定义版本的报告内容静默覆盖历史。

### P0-2：岗位设置与准备度 API

目标：建立唯一当前目标岗位上下文和透明的准备度估计。

- 支持简历版本选择与可选 JD 存储/解析边界。
- 从岗位基线与用户证据生成岗位技能要求。
- 定义准备度构成权重、置信度规则和版本化公式。
- 新增有界的岗位设置、岗位技能图、技能状态和准备度摘要 API。

验收标准：

- 无 JD 用户可以继续，但明确使用证据覆盖较低的岗位基线。
- 准备度 API 返回构成项、证据数/置信度、来源时间和“估计值”语义。
- 不泄露其他用户的简历、JD、面试或证据。

风险：JD 导入带来 PII、Prompt Injection、保留策略和 Provider 成本要求；权重必须经数据校准，不能作为招聘模型。

### P0-3：面试模式与选题合同

目标：支持完整模拟和单技能练习，同时不削弱现有流式面试。

- 持久化面试模式、目标岗位、选定技能、题目元数据和父子追问关系。
- 按目标岗位、技能缺口、难度和题目历史对有界检索候选集排序。
- 完整模拟在结束前不展示评价；技能练习的即时反馈规则必须明确。

验收标准：

- 现有 SSE、资源归属、简历确认、成本和 checkpoint 持续可用。
- 题目与追问拥有稳定标识和选择/评价元数据。
- 候选人事件不包含 Prompt、RAG、工具和模型内部信息。

风险：SSE Payload 改动属于跨客户端合同改动，必须有兼容性测试。

### P0-4：训练产品 Web 壳

目标：在 API 可信后，用现有 React 应用交付候选人训练闭环。

- 新增首页、练习、面试记录、技能、报告、使用量和设置的应用导航。
- 用准备度、缺口、最近表现和下一步行动替代 Token/工具优先的首页。
- 拆分面试房间、评价报告和回放为独立路由/组件。
- 根据 `DESIGN_SYSTEM.md` 建立共享 P0 基础组件，同时保留现有管理员路由。

验收标准：

- 首次用户可在桌面和移动端从岗位设置走到报告。
- 回访用户看到准确的下一步行动，或明确的证据不足状态。
- UI 不会把缺失后端数据展示为已完成的训练/准备度结论。
- Web 单测、typecheck/build 和浏览器验收覆盖主路径与空/错误状态。

风险：在 P0-1 至 P0-3 前先重写视觉界面会制造虚假的产品数据和不稳定合同。

### P0-5：训练推荐、回放与比较

目标：让完成评价自然进入定向练习和可比复面。

- 从明确缺口证据生成推荐。
- 跟踪训练完成情况，将重试与原始证据关联。
- 仅比较技能、规则和难度可比的尝试，并披露低置信度。

验收标准：每项推荐关联缺口证据；回放保留不可变的原题、回答、追问和评价；比较同时解释分数和证据变化。

### P0-6：使用量边界与评价发布门

目标：保护模型驱动价值，避免未验证的评估器变更。

- 按用户和周期聚合现有 SessionCost。
- 在展示额度 UI 前增加服务端权益策略点。
- 版本化评估器/Prompt/规则输入并记录 Harness 运行。
- 用数据集对比与发布决策控制评估器/运行时变更。

验收标准：前端无法绕过后端/Gateway 策略；使用量在定义周期和鉴权范围内准确；Agent/评估器变更上线前有对照/实验决策记录。

## 首个实现任务

从 P0-1 开始，并保持为单独实现任务。不要在同一个 PR 中混合 Schema 改动、岗位设置、SSE 改动和前端壳。P0-1 是后续所有候选人结论可信的基础。

## 影响摘要

| 领域 | P0 影响 |
| --- | --- |
| 架构 | 保持模块化单体；围绕已有面试/报告数据增加领域合同。 |
| 数据库 | 需要规范化的目标岗位、技能、证据和评估记录，并保持用户归属。 |
| API | 新增带鉴权、资源归属的岗位/准备度/技能/证据 API；SSE 改动推迟到 P0-3。 |
| 安全 | 扩展现有 JWT/RBAC/ownership，并审查敏感 JD/证据保留策略。 |
| 成本 | 所有新增 AI 处理经 LLM Gateway；要求有界导入和明确成本指标。 |
| 测试 | 增加 migration、鉴权隔离、评估合同、选题、Web、浏览器和 Harness 对比覆盖。 |
